## 1. Why revisit the surface now?

aikata has accumulated useful capabilities through v0.8.5: canonical
documents, per-AI-tool generation, `doctor`, `sync`, opt-in components,
stack-specific guidance, monorepo support, and workflow guides.

The next risk is no longer missing capability. It is that the growing
surface obscures the answer to a simpler question:

> What does aikata do for human-AI collaboration?

The maintainer's concern is that a tool intended to reduce documentation
maintenance can become another system whose axes, generated files, and
configuration require explanation and upkeep. Rich future possibilities
are useful as direction, but they must not become the product's center of
gravity before the core loop is crisp.

---

## 2. Core concept

aikata exists to reduce the manual cost of keeping project context
readable and consistent while giving humans and AI coding agents a shared
understanding of the work.

Its core loop is:

```text
canonical human-and-AI-readable documents
    -> generated disposable tool-specific artifacts
    -> consistency checks with doctor
    -> non-destructive template maintenance with sync
```

The product is not a project generator, a best-practice encyclopedia, an
LLM agent personality, or a plugin marketplace. It scaffolds and
maintains the document structure that lets a human and an AI agent work
from the same source of truth.

This implies a simple test for every feature:

> Does this materially reduce context-maintenance work or prevent a
> recurring human-AI collaboration failure?

If the answer is unclear, defer the feature until dogfooding evidence
sharpens it.

---

## 3. What remains core?

| Surface | Why it stays |
|---|---|
| `aikata init` | Creates a coherent starting structure without requiring each project to invent one. |
| Canonical `AGENTS.md` plus dual-readable docs | Gives humans and agents one shared source of truth. |
| `aikata generate` | Removes duplicate maintenance across AI-tool-specific instruction files. |
| `aikata doctor` | Detects drift and broken document contracts before they become collaboration failures. |
| `aikata sync` | Applies template improvements without silently overwriting project edits. |
| Small opt-in documents | Lets projects add only the context slots they need while preserving Do-No-Harm. |

`doctor` and `sync` have non-trivial internals. That complexity is
justified only where it removes work or protects user-owned content. The
normal user path should not require understanding manifests, merge
classification, or exclusion mechanics.

## 4. Evidence of excess or drift

### 4.1 Dogfooding documentation drift

The repository currently contains stale live references despite aikata's
document-centered positioning:

- `README.md` still labels the product status as v0.2 while the current
  release tag is v0.8.5.
- `README.md`'s ADR index stops at ADR 0019 even though later accepted
  decisions exist.
- `SPEC.md` still documents the removed `aikata add` command instead of
  the v0.7.1 `enable` / `new` taxonomy.
- `ROADMAP.md` still marks released v0.8.2 and v0.8.3 work as pending.
- `docs/adoption.md` and the repository's own `.aikata/aikata.yaml`
  still reference the removed `docs.generate_gitignore` field.

The first v0.9.0 task is to repair this drift and identify which checks
would have caught it. Dogfooding must validate the product promise.

### 4.2 Standard scaffold breadth

`aikata init --scope standard` currently emits several useful canonical
documents plus empty starter documents. Each file increases the amount of
surface a human and an agent must scan and maintain.

The highest-priority audit candidate is `docs/prompts.md`: it is empty at
init time, is not required for the canonical rules / memory / working
state model, and does not yet have dogfooding evidence strong enough to
justify default inclusion.

The audit is not a mandate to minimize file count mechanically. A file
stays default-on when it has a distinct lifetime and repeatedly saves
context reconstruction work.

### 4.3 `doctor` default scope

`doctor` currently walks repository Markdown broadly and requires
aikata's five-key frontmatter on files that may be governed by another
contract. ADR 0021 added `doctor.exclude` after a real Claude Code plugin
layout triggered false positives.

The exclusion list is a valid escape hatch, but the incident suggests a
boundary question: should the default validator inspect every Markdown
file, or primarily the document surface aikata manages?

The leading direction is a narrower managed-document default with an
explicit broader audit mode. The exact pre-manifest and adoption
semantics need a follow-up ADR before implementation.

### 4.4 Stack guidance depth

The Flutter and TypeScript stack briefs are useful, but parts read as a
general best-practice pack rather than collaboration-critical guardrails.
Examples include committing every generated Dart file, requiring tests
for every reusable widget, and pinning detailed TypeScript compiler
preferences.

The intended stack boundary is smaller:

- prevent common AI mistakes;
- name the minimum verification commands;
- point to the project's ADRs for choices;
- leave project-specific policy to downstream edits.

Refactoring duplicated preset trees into a scope base plus stack
partials is useful only as an internal drift-reduction measure. It must
not become a reason to proliferate stacks or unlock a plugin platform.

## 5. Outcome

The tranche shipped across v0.9.0 – v0.9.2. The target mental model —
`init` (place the shared structure) → `generate` (derive disposable
AI-tool files) → `doctor` (check coherence) → `sync` (adopt template
improvements without losing edits) → `enable` (opt into a few extra
context slots) — is the surface the current README and SPEC describe.

The five work packages (§1–§4 rationale) landed as follows; the binding
records are the ADRs and the [CHANGELOG](../../CHANGELOG.md):

- **Live-document convergence** — README/SPEC/ROADMAP/adoption/dogfood
  config realigned to the shipped surface (v0.9.0/v0.9.1).
- **Default scaffold audit** — `docs/prompts.md` moved to the opt-in
  `prompts` capability
  ([ADR 0034](../adr/0034-reusable-prompts-opt-in-capability.md), v0.9.2),
  resolving the former Q-DESIGN-12.
- **`doctor` scope redesign** — direction set by
  [ADR 0033](../adr/0033-doctor-default-scope-direction.md) and the
  behavior shipped in v0.9.7
  ([ADR 0037](../adr/0037-tighten-adoption-mutation-boundaries.md) D1),
  resolving the former Q-DOCTOR-02 direction.
- **Stack-brief simplification** — code-free layout convention
  ([ADR 0029](../adr/0029-stack-brief-layout-convention.md)) plus the
  subtractive trim
  ([ADR 0030](../adr/0030-trim-stack-briefs-to-standard-guardrails.md)),
  resolving the former Q-DESIGN-13.
- **Roadmap pruning** — v1.0 requirements re-evaluated against the
  core-concept test; speculative ecosystem work kept off the critical
  path (see [ROADMAP.md](../../ROADMAP.md)).

The tranche's explicit non-goals — new stack families, multi-stack
composition, external stack repositories, new workflow-guide domains,
third-party skill/plugin management, AI-assisted drafting, and
source/dependency/CI generation — remain deferred, not rejected, pending
dogfooding evidence.
